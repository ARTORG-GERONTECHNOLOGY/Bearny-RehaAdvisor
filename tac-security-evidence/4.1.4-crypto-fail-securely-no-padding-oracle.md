# Evidence — 4.1.4: Cryptographic modules fail securely — no Padding Oracle

## Summary

Fernet (used for token-at-rest encryption) is an authenticated encryption
scheme — it verifies the HMAC before attempting decryption. Any ciphertext
tampering causes an `InvalidToken` exception before any plaintext is produced,
eliminating the Padding Oracle attack surface.

---

## Fernet authenticated decryption

File: `backend/core/encrypted_field.py`

```python
def to_python(self, value):
    if value is None:
        return None
    try:
        return _fernet().decrypt(value.encode()).decode()
        # Fernet.decrypt():
        # 1. Verifies HMAC-SHA256 first — any tampering → InvalidToken immediately
        # 2. Only decrypts (AES-128-CBC) if HMAC is valid
        # This prevents Padding Oracle: the decryption result is never observable
        # when the HMAC check fails.
    except (InvalidToken, Exception):
        # Legacy plaintext value — return as-is
        return value
```

**Why this prevents Padding Oracle:** In a Padding Oracle attack, the attacker
needs a way to distinguish "bad padding" from "valid padding" responses. Fernet
rejects any tampered ciphertext at the HMAC stage — before the AES-CBC
decryption runs — so the attacker never receives a padding-related signal.

---

## TLS — no CBC cipher suites with known Padding Oracle issues

The nginx cipher suite (see 4.1.3) includes only GCM and ChaCha20-Poly1305
modes. No CBC-mode TLS cipher suites (which could be vulnerable to BEAST or
Lucky13) are configured.

---

## JWT — no Padding Oracle risk

JWTs use HS256 (HMAC-SHA256 signature), not RSA-OAEP or RSA-PKCS1.
There is no asymmetric encryption in the JWT stack; hence no Padding Oracle
attack surface from token validation.
