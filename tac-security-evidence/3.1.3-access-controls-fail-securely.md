# Evidence — 3.1.3: Access controls fail securely including on exceptions

## Summary

All authentication and authorisation checks use explicit allow-lists with a
deny-by-default posture. Exception handlers return HTTP 401/403 — never
silently allow the request through.

---

## JWTAuthMiddleware — deny on any token error

File: `backend/core/middleware.py`

```python
try:
    token = AccessToken(token_str)
except (TokenError, Exception):
    # Any token error → 401, not pass-through
    return JsonResponse(
        {"detail": "Given token is not valid or has expired."},
        status=401,
    )
```

If token validation raises any exception (invalid format, wrong signature,
expired, Redis unavailable for JTI check) the request is rejected.

---

## Redis failure mode — fail open for availability, deny on revocation errors

File: `backend/core/token_revocation.py`

```python
def is_jti_revoked(jti: str) -> bool:
    try:
        rc = _get_redis()
        return rc.exists(f"{_NONCE_PREFIX}{jti}") > 0
    except Exception:
        logger.exception("[token_revocation] Redis error in is_jti_revoked(%s)", jti)
        # Fail open: if Redis is down, don't lock out users.
        return False
```

The documented trade-off: if Redis is unavailable the JTI check fails open
to preserve availability. This is acceptable because token expiry (5 min
access / 1 day refresh) still limits the window. The per-user `valid_from`
check has the same behaviour. Both are documented design decisions.

## IsAdmin permission — deny on any DB error

File: `backend/core/permissions.py`

```python
def has_permission(self, request, view):
    if not getattr(request.user, "is_authenticated", False):
        return False
    try:
        user = User.objects.get(pk=ObjectId(request.user.id))
        return user.role == "Admin" and user.isActive
    except Exception:
        return False   # ← deny on any DB error
```

If the user lookup fails for any reason, access is denied.
