# Evidence — 3.2.1: Secure OAuth 2.0 flows — Authorization Code Flow only

## Summary

Both wearable integrations (Fitbit and Google Health) use the **OAuth 2.0
Authorization Code Flow** exclusively. The Implicit Flow and Resource Owner
Password Credentials Flow are not used.

---

## Fitbit — Authorization Code Flow

File: `backend/core/views/fitbit_view.py`

The callback receives an authorization `code` from Fitbit and exchanges it
for tokens via a server-to-server POST (client secret is never exposed to
the browser):

```python
data = {
    "grant_type": "authorization_code",
    "code": code,
    "redirect_uri": settings.FITBIT_REDIRECT_URI,
}
response = requests.post(token_url, auth=basic_auth, data=data, headers=headers)
```

- Authorization code is single-use and short-lived
- Token exchange happens server-side (client secret stays on server)
- Tokens are never returned to the browser URL

---

## Google Health — Authorization Code Flow

File: `backend/core/views/google_health_view.py`

```python
# Callback receives ?code=... and exchanges it server-side
code = request.GET.get("code")
...
token_response = requests.post(
    "https://oauth2.googleapis.com/token",
    data={
        "grant_type": "authorization_code",
        "code": code,
        "redirect_uri": settings.GOOGLE_HEALTH_REDIRECT_URI,
        "client_id": settings.GOOGLE_HEALTH_CLIENT_ID,
        "client_secret": settings.GOOGLE_HEALTH_CLIENT_SECRET,
    },
)
```

## Frontend — no token in URL

File: `frontend/src/utils/googleHealthAuthUrl.ts`

The frontend generates the authorization URL and redirects the user to
Google's OAuth endpoint. The `response_type=code` parameter is used (not
`response_type=token` which would be the Implicit Flow).

```typescript
const params = new URLSearchParams({
  response_type: 'code',
  client_id: ...,
  redirect_uri: ...,
  scope: ...,
  state: `${nonce}:${patientId}`,
  access_type: 'offline',
});
```
