# Evidence — 5.1.1: Protection against HTTP parameter pollution

## Summary

The application uses Django's standard `QueryDict` for URL parameters and
`json.loads(request.body)` for request bodies. Both handle duplicate
parameters deterministically and do not expose a parameter pollution attack
surface.

---

## Django QueryDict behaviour

Django's `QueryDict` returns the **last** value for duplicate query parameters
(via `.get()`) or all values as a list (via `.getlist()`). Views use `.get()`
for single-value parameters, which is consistent and not exploitable.

```python
# All views use explicit key extraction:
patient_id = request.GET.get("patientId")
# or
data = json.loads(request.body)
user_id = data.get("userId")
```

No view uses `request.GET` in a way that would allow a second parameter to
shadow a security-critical value (e.g. passing `?role=Admin&role=Patient`
would return `Patient` — the last value — not `Admin`).

---

## JSON body — no duplicate key ambiguity

The `json.loads()` call uses Python's standard library parser, which returns
the **last** value for duplicate JSON keys, consistent with RFC 7159 guidance.
No security-critical field is read in a way that depends on key ordering.

---

## No framework known to be vulnerable

Django does not have the HPP vulnerabilities historically found in PHP's
`$_GET`/`$_POST` array coercion behaviour.
