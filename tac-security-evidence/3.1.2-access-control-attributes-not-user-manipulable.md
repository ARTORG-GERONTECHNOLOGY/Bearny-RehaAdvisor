# Evidence — 3.1.2: Access control attributes not manipulable by end users

## Summary

Role, clinic membership, and patient ownership are resolved server-side from
the JWT payload and MongoDB records — never from user-supplied request
parameters. Callers cannot escalate their role or claim another user's data
by modifying a request body field.

---

## Role derived from JWT (server-signed)

File: `backend/core/middleware.py`

```python
token = AccessToken(token_str)           # validates signature
user_id = str(token.payload.get("user_id", ""))
# role is in the token payload — set at login, signed by SECRET_KEY
```

The role claim is embedded in the JWT at login time and cannot be changed
by the client. Any modification to the token payload invalidates the HS256
signature.

---

## Clinic membership from database, not request

File: `backend/core/views/patient_views.py`

```python
# Therapist's clinics come from the DB, not from the request
caller_therapist = get_therapist_for_user(request.user)
patient_clinic = getattr(patient, "clinic", None)

if not caller_therapist or patient_clinic not in (caller_therapist.clinics or []):
    return JsonResponse({"error": "You are not authorised to access this patient's data."}, status=403)
```

A caller cannot pass `?clinic=InselspitalBern` to gain access to a different
clinic's patients — the check always reads from the authenticated user's
database record.

---

## therapistId from DB, not request body

File: `backend/core/views/patient_views.py` — `add_intervention_to_patient`

The therapist identity used for ownership is resolved from the authenticated
user's JWT/DB record. User-supplied `therapistId` in the request body is only
used as a secondary lookup key after the caller's identity is established.
