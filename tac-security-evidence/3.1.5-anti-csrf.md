# Evidence — 3.1.5: Strong anti-CSRF mechanism

## Summary

CSRF is mitigated by two complementary controls that together eliminate the
attack surface without requiring a traditional CSRF token:

1. **`SameSite=Strict` cookies** — browsers do not send the auth cookies on
   cross-site requests, so a cross-origin form or `fetch()` call cannot carry
   the session.

2. **`Authorization: Bearer` header requirement** — API clients that use the
   header (instead of cookies) are inherently CSRF-safe because browsers never
   automatically add custom headers to cross-site requests.

---

## SameSite=Strict on all auth cookies

File: `backend/core/views/auth_views.py`

```python
response.set_cookie("access_token",  ..., samesite="Strict")
response.set_cookie("refresh_token", ..., samesite="Strict")
```

`SameSite=Strict` prevents the cookies from being sent on any cross-site
navigation, including `<form action="...">` submits and background `fetch()`
calls from third-party pages.

---

## Content-Security-Policy — restricts request origins

File: `nginx/conf/prod.reha-advisor.nginx.conf`

```nginx
add_header Content-Security-Policy
  "default-src 'self';
   connect-src 'self' https://*.sentry.io https://*.ingest.sentry.io;
   frame-ancestors 'none';" always;
```

`connect-src 'self'` restricts XHR/fetch to the same origin.
`frame-ancestors 'none'` prevents clickjacking.

## Note on @csrf_exempt decorators

Some views use `@csrf_exempt`. This does not weaken security because:
- Django's CSRF middleware protects browser form submissions; these endpoints
  are JSON APIs consumed by the React SPA via `fetch()` with the
  `Authorization` header, not by HTML forms.
- The `SameSite=Strict` cookie attribute provides equivalent CSRF protection
  for cookie-based callers.
- All endpoints still require a valid JWT — an unauthenticated CSRF attempt
  receives HTTP 401.
